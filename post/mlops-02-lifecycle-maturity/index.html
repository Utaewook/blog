ML 라이프사이클과 성숙도

2026년 11월 2일
5 minute read

지난 글에서는 모델을 만드는 과정이나 그 이후의 과정에서 생기는 문제와 경험들을 MLOps의 기본적인 개념과 함께 연결해서 정리해봤다. 모델이 어디서 나왔는지 추적이 안 되고, 성능은 조용히 떨어지고, 재학습과 배포는 사람이 직접 하는 문제를 해결하자는게 핵심!

이 문제들은 모델이 만들어지고 운영되는 흐름의 어느 지점에서 생긴다. 그래서 그 흐름(ML 라이프사이클)을 단계별로 나눠 보고, 어디까지 자동화했느냐로 수준을 나눈 성숙도 모델 두 가지를 정리했다. “MLOps를 도입한다"는 말이 처음엔 꽤 막연했는데, 성숙도 모델을 보고 나니 다음에 뭘 해야 하는 지와 어느 정도의 구축을 목표로 해야 할 지가 좀 보였다.

ML 라이프사이클

이전 프로젝트에서 겪은 일들을 순서대로 놓으면 대략 이런 흐름이 된다. (거의 대부분의 기본적인 AI 활용 서비스는 비슷할 것)

  1. 데이터를 모으고 라벨링한다
  2. 데이터를 들여다보고, 전처리해서 모델에 맞게 바꾼다
  3. 모델을 학습시킨다
  4. 테스트하고 검증한다
  5. 포맷을 변환해서 추론 서버에 올린다
  6. 운영하면서 결과를 지켜본다

Google Cloud의 MLOps 문서는 이걸 8단계로 더 잘게 쪼개는데, 평가와 검증을 나눠 둔 게 눈에 띈다.

  • 평가(evaluation): 테스트 데이터로 성능 지표를 뽑는다.
  • 검증(validation): 그 성능이 기준선(baseline)보다 나아서 배포해도 되는지 판단한다.

일반 소프트웨어 개발 흐름과 비교하면, 모델과 데이터의 영역까지 들어오며 조금 더 많은 단계를 거친다는 점이다.

앞쪽(데이터~검증)과 뒤쪽(서빙~모니터링)의 성격 또한 다르다.

  • 앞쪽은 실험: 노트북과 스크립트로 이것저것 시도해 본다.
  • 뒤쪽은 운영: 서비스를 안정적으로 굴린다.

이 둘을 다른 사람이 맡거나 다른 코드로 돌리면 “학습 때 쓴 전처리와 추론 때 쓴 전처리가 다르다” 같은 문제가 생긴다. Google 문서는 이걸 training-serving skew라고 부른다.

성숙도 모델은 왜 보나

라이프사이클의 모든 단계를 한 번에 자동화할 수는 없고, 그럴 필요도 없다. “지금 어디쯤이고 다음에 뭘 붙여야 하나"를 판단하는 기준이 성숙도 모델이다. 많이 인용되는 건 두 가지다.

  • Google: Level 0~2의 3단계. 무엇을 자동화했는지를 기준으로 나눔
  • Microsoft: Level 0~4의 5단계. 기술뿐 아니라 팀이 어떻게 같이 일하는지 확장

Google의 MLOps Level 0/1/2

Level 0: 수동 프로세스

모든 단계를 사람이 스크립트나 노트북으로 직접 돌리고, 만든 모델 파일을 운영 쪽에 넘겨 배포한다. 모델 교체는 드물다.

돌아보면 이전 CBM 프로젝트의 운영 방식이 거의 이 단계라 생각된다. 실험의 자세한 기록은 노트와 로그에 흩어져 있었고, 재학습과 배포는 사람이 직접 했다. 모델이 자주 바뀌지 않는다면 Level 0으로도 버틸 만하다. 문제는 데이터가 바뀌어서 모델을 자주 갈아 끼워야 할 때다.

Level 1: ML 파이프라인 자동화

CT가 목표인 단계!

학습 과정을 파이프라인으로 묶어 두고, 새 데이터가 들어오면 파이프라인이 알아서 다시 학습하고 검증해서 모델을 내보낸다.

Level 0과 가장 크게 다른 건 배포 대상이다. 학습이 끝난 모델이 아니라 모델을 만드는 파이프라인 자체를 운영 환경에 배포한다. 그래서 실험 때 쓰던 파이프라인과 운영 파이프라인이 같은 코드가 되고, 앞에서 말한 training-serving skew도 줄어든다.

사람 없이 돌리려면 이런 것들이 더 필요하다.

  • 데이터 검증: 학습 전에 스키마와 값 분포를 확인해서, 다시 학습할지 멈출지 정한다.
  • 모델 검증: 새 모델이 운영 중인 모델보다 나을 때만 내보낸다.
  • 메타데이터 관리: 언제, 어떤 데이터와 파라미터로 돌았고 무엇을 만들었는지 기록한다.
  • 파이프라인 트리거: 요청, 일정, 새 데이터 도착, 성능 저하, 데이터 분포 변화.
  • 피처 스토어: 선택 사항.

한계는 파이프라인 자체를 고치는 게 여전히 수동이라는 점이다. 새 피처나 모델 구조를 시도할 때마다 파이프라인 코드를 손으로 테스트하고 배포해야 해서, 파이프라인이 많아지면 감당이 안 된다.

Level 2: CI/CD 파이프라인 자동화

Level 1에서 수동으로 남았던 파이프라인 코드 변경까지 CI/CD로 자동화한다. 실험으로 만든 파이프라인 코드가 CI(빌드, 테스트)와 CD(운영 배포)를 거쳐 올라가고, 배포된 파이프라인이 모델을 학습시켜 레지스트리와 예측 서비스로 내보낸다.

그래도 데이터 분석과 모델 분석은 Level 2에서도 사람이 한다. 반복되는 일은 맡기고, 판단은 여전히 사람 몫이라는 얘기로 읽혔다.

Microsoft의 MLOps 성숙도 모델

Microsoft는 Level 0~4의 5단계로 나누고, 각 단계를 사람, 모델 생성, 모델 릴리스, 애플리케이션 통합 네 관점에서 따로 본다.

레벨특징
0전부 수동. 실험 기록이 일정하지 않고, 모델 파일을 손으로 넘긴다
1애플리케이션 빌드와 테스트는 자동화. 모델은 여전히 추적, 재현이 어렵다
2학습 자동화, 실험 결과 추적, 학습 코드와 모델 버전 관리. 릴리스는 수동
3릴리스까지 CI/CD로 자동화. 배포된 모델에서 원본 데이터까지 추적
4운영 지표가 재학습을 자동으로 트리거

여기서 눈여겨본 건 두 가지다.

  • 사람: 낮은 레벨에서는 데이터 사이언티스트, 데이터 엔지니어, 소프트웨어 엔지니어가 따로 일하고 모델을 넘겨받는다. 레벨이 오를수록 같이 일한다. 도구만 붙인다고 레벨이 오르는 게 아니다.
  • 순서: 실험 추적과 모델 버전 관리(Level 2)가 배포 자동화(Level 3)보다 먼저 온다.

핵심

모델이 어디서 나왔는지 모르는 상태에서 배포만 자동화하면, 출처 모를 모델이 더 빨리 나갈 뿐이다.

그래서 실험 추적부터 공부해 보려고 한다.

두 모델은 자르는 기준이 달라 1:1로 맞지 않지만, 대략 Google Level 0이 Microsoft Level 01, Google Level 12가 Microsoft Level 2~4에 해당한다.

정리

  • ML 라이프사이클은 데이터 → 학습 → 평가, 검증 → 서빙 → 모니터링으로 이어지고, 모니터링에서 다시 데이터와 학습으로 돌아가는 고리다.
  • 성숙도 모델로 보면 실험 추적과 모델 버전 관리가 먼저고, 서빙, 파이프라인, 모니터링이 그 위에 붙는다.
