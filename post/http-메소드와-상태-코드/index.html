HTTP 메소드와 상태 코드

Mar 28, 2026
4 minute read

HTTP 요청과 응답 과정이서 HTTP 메소드와 상태 코드에 대한 내용을 다뤄 봤는데, 이번엔 이 메소드와 상태 코드의 대표적인 것들을 살펴볼 예정이다.

1. HTTP 메소드

HTTP 메소드는 클라이언트가 서버에게 어떤 동작을 수행하길 원하는지를 나타내는 방법이다. 주로 쓰이는 메소드는 아래와 같다.

  1. GET
    • 서버로부터 특정 리소스를 요청한다. 이는 웹페이지 또는 이미지를 요청하는 데 사용 가능하며, 데이터를 변경하지 않고 읽어오는 역할을 한다.
  2. POST
    • 서버에 데이터를 제출해 리소스를 생성/추가한다. 이는 폼 제출, 메시지 게시 등 데이터를 서버에 적을 때 사용한다.
  3. PUT
    • 지정된 URI에 리소스를 생성하거나, 이미 존재하는 경우 업데이트한다. 파일 업로드, 콘텐츠 수정 등 기존 리소스를 대체하거나 생성하는 데 사용된다.
  4. DELETE
    • 지정된 URI의 리소스를 삭제하는 동작을 수행한다. 게시물, 사용자 계정 삭제등의 기능에 사용된다.
  5. HEAD
    • GET과 유사하지만, 응답 본문 없이 헤더 정보만 가져오는 역할을 한다. 리소스의 메타데이터나 상태를 확인할 때 사용되며, 본문 데이터를 다운로드하지 않고 리소스 정보를 확인할 수 있다는 특징이 있다!
  6. OPTIONS
    • 타겟 리소스에 대한 통신 옵션을 설명한다. 서버나 특정 리소스의 기능을 확인하며, CORS(Cross-Origin Resource Sharing) 처리에 중요하다.
  7. PATCH
    • 리소스의 부분적인 업데이트를 수행한다. PUT과 달리 전체를 대체하지 않고 일부만 수행한다는 점이 있다.

데이터 처리의 기본 기능인 CRUD에 대응되는 메소드들이 존재함을 알 수 있다. Update 기능에 있어서 PUT과 PATCH의 차이점은 수정 범위가 전체인지, 부분인지를 통해 어느 정도 감이 잡히는데. PUT과 POST의 데이터 입력에 있어서 살짝 헷갈리는 점이 있다.

PUT과 POST의 차이는 멱등성에 있다고 한다. 두 메소드를 다시 한번 자세히 살펴보면

PUT

  • 주요 용도: 리소스의 전체 교체 또는 새 리소스의 생성에 사용된다.
  • Idempotent: PUT은 멱등성을 갖는다. 이는 같은 요청을 여러 번 수행해도 결과가 동일함을 의미한다. 예를 들어 같은 데이터로 같은 URI에 PUT 요청을 여러 번 하더라도, 첫 번째 이후의 요청은 추가적인 변화를 일으키지 않는다.
  • 데이터 지정: 클라이언트는 URL을 포함하여 업데이트하거나 생성할 리소스의 전체 내용을 제공해야 한다.
  • 예시로는 특정 사용자 전체 프로필 정보를 업데이트하거나, 지정된 URL에 새로운 문서를 만드는 경우에 사용된다.

POST

  • 주요 용도: 새 리소스를 생성하거나, 서버에서 처리할 데이터를 전송하는 데 사용된다.
  • Non-idempotent: POST는 비멱등성으로, 같은 POST 요청을 여러 번 보내면, 서버에 여러 개의 리소스가 생성될 수 있다.
  • 서버의 역할: POST 요청은 서버에게 데이터를 처리하도록 요청하며, 이 처리 방식은 서버에 의해 결정된다. 서버는 데이터를 받아 새로운 리소스를 생성하거나, 다른 동작을 수행할 수 있다.
  • 예시로는 블로그에 새 게시물을 게시하거나, 사용자가 폼을 제출하는 경우에 사용된다. 같은 블로그 글로 같은 URL에 반복적으로 수행하면, 같은 게시물이 계속 다시 생성됨

차이점을 요약해 보자면 우선 목적과 행동에서 차이가 있다. PUT은 기존 리소스를 대체하거나 새 리소스를 지정된 URL에 생성하는 데 사용되며, POST는 서버가 요청된 데이터를 처리해 새로운 리소스를 생성하는 데 사용된다는 점이다.

또한, 멱등성에 있어서 차이가 있는데, PUT은 같은 요청을 반복해도 같은 결과를 내게 되지만, POST는 같은 요청을 반복하면 서로 다른 결과(여러 개의 리소스 생성)를 나타낸다.

그리고 리소스의 위치에 있어서도 차이가 있는데, PUT의 경우에는 리소스의 위치를 URL을 통해 클라이언트가 직접 결정하는 반면, POST는 서버가 새 리소스의 위치를 결정한다.

위의 7가지 메소드 외에도, CONNECT, TRACE라는 메소드가 HTTP/1.1 표준으로 존재하는데, GET/POST/PUT/DELETE 에 비해 조금 덜 일반적이다 보니 생략을 하였다. 간단히 짚고 넘어가면, CONNECT는 프록시 서버를 통해 터널을 설정하는 데 사용되고, TRACE는 요청을 디버깅하는 데 사용된다고 한다.

2. HTTP 상태 코드

HTTP 상태 코드는 서버가 클라이언트의 요청을 어떻게 처리했는지 알려주는 코드이다. 우리가 흔하게 접해봤던 404 Not Found와 같은 게 이 상태 코드~~(와 텍스트)~~이다! 상태 코드의 종류는 아주 다양하지만, 가장 앞자리(100의 자리 수)를 통해 어느 정도 분류가 가능하다.

  • 1 - - (정보 응답)
    • 클라이언트에게 요청의 초기 부분이 수신되었고, 나머지를 계속 보내도 좋음을 알리는 코드이다.
    • 예시: 100 Continue, 101 Switching Protocols…
  • 2 - - (성공)
    • 요청이 성공적으로 수행되었음을 알리는 코드이다. 
    • 예시: 200 OK, 201 Created, 204 No Content…
  • 3 - - (리다이렉션)
    • 요청된 리소스가 다른 위치로 이동했거나 변경되지 않았음을 나타내는 코드이다.
    • 예시: 301 Moved Permanently, 302 Found, 304 Not Modified… 
  • 4 - - (클라이언트 오류)
    • 클라이언트 측에서 오류가 발생했음을 나타내는 코드이다.
    • 예시: 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found…
  • 5 - - (서버 오류)
    • 서버 측에서 오류가 발생했음을 나타내는 코드이다.
    • 예시: 500 Internal Server Error, 501 Not Implemented, 503 Service Unavailable…

예시 이 외에도 다양한 상태 코드가 있다. 이에 대한 자세한 설명은 출처에 기재되어 있는 mozilla의 ‘개발자를 위한 웹 기술’ 문서에서 확인해 볼 수 있다. 

HTTP의 메소드와 상태 코드를 이해하는 것은 서버와 클라이언트가 어떻게 요청을 응답하고 처리했는지에 대한 이해를 돕는다. 이를 통해 클라이언트의 요청이 성공적으로 처리되었는지, 문제가 발생했다면 그 원인이 무엇인지를 파악할 수 있다!
