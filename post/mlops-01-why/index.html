MLOps?

2026년 10월 29일
4 minute read

서론

지금까지 업무를 진행하면서 아래와 같은 부분들을 경험했다.

  • 데이터를 라벨링/분류하기
  • 전처리 코드를 작성하고 데이터를 모델에 적합하게 바꾸기
  • 모델을 학습시키고 테스트, 검증하기
  • 적절한 포맷으로 변환하고, 실제로 추론까지 해보기
  • 데이터를 적재하고 전처리, 추론까지 하는 파이프라인 구성하기

해당 경험들은 CBM(상태 기반 유지 보수) 서비스와 사내 범용 데이터 분석 파이프라인 플랫폼 프로젝트를 진행하며 쌓았다.

이들은 나를 머신러닝 엔지니어로서 성장하게 했고, 데이터와 모델을 바라보는 시각을 길러 주었다.

다만, 여러 부분에서 문제가 나왔다. 어떤 문제였는지는 아래에서 풀어 보겠다.

현재는 사내 플랫폼 프로젝트의 다음 스텝으로 “학습과 추론을 체계적으로 관리하는 MLOps 도입” 업무를 맡게 되었다.

그래서, 이전 CBM 프로젝트에서 겪었던 불편함과 파이프라인 설계 및 구현 경험을 기반으로, 사내 플랫폼에 MLOps를 적용하기 위해 MLOps에 대해 내가 배우는 것들을 정리하려 한다.

모델을 만들며 생기는 문제

모델을 만들고 추론만 하면 끝이 아니었다.

CBM 서비스를 운영할 땐 학습시킨 모델들이 여러 디렉토리에 흩어져 있다든가, 어떤 모델과 전처리가 최적이었고 그때 사용한 데이터가 뭐였는지 추적하기가 어려웠다.

필요에 따라 서비스에서 내보내는 로그 파일을 직접 뒤져보거나, DB에 저장된 것들을 직접 보고, 과거의 내가 직접 노트에 작성한 기록들을 대조하면서 꾸역꾸역 성능 지표와 모델, 전처리 등을 재현해내긴 했지만 썩 유쾌한 경험은 아니었다. 리눅스 활용 능력, 로그 작성이나 여러 요소를 기록하는 습관을 기르는 데는 긍정적이었지만 모델을 학습하고 추론하는 사용자 측면에서는 영 꽝이었던 것.

결국 지속적으로 사용 가능한 시스템으로의 발전을 위해서는 여러 가지가 관리되어야 한다.

  • 코드/데이터/파라미터 등 여러 학습에 영향을 끼치는 요인
  • 현재 모델이 구체적으로 어떤 실험의 어떤 단계에서 나왔는지
  • 추론 쪽에서 입력 데이터가 바뀌면 성능이 조용히 떨어지는 문제
  • 재학습과 배포를 사람이 직접 하는 번거로움

해당 경험에 대한 MLOPS로의 해결도 차차 다룰 예정이다.

ML 시스템의 숨은 기술 부채

MLOps 얘기를 할 때 거의 빠지지 않는 2015년 논문이 있다. 내용은 대충 실제 ML 시스템에서 모델 코드는 아주 작은 부분이고, 나머지 대부분은 그 모델을 굴리기 위한 주변 코드와 인프라라는 것.

데이터 수집, 데이터 검증, 피처 추출, 설정, 리소스 관리, 서빙 인프라, 모니터링. 모델 하나를 서비스로 내보내려면 이것들이 다 붙어야 한다. 논문은 여기에 일반 소프트웨어에는 없는 종류의 부채가 쌓인다고 말하는데, 이 글과 관련 있는 것만 추리면 이렇다.

  • 하나를 바꾸면 전부 바뀐다 (CACE): 모델은 입력 피처들을 섞어서 쓰기 때문에, 피처 하나나 하이퍼파라미터 하나만 바꿔도 전체 동작이 바뀐다.
  • 데이터 의존성: 코드 의존성은 컴파일러가 잡아 주지만, 모델이 사용하는 데이터가 바뀌는 건 아무도 알려 주지 않는다.
  • 피드백 루프: 모델의 예측이 다음 학습 데이터에 영향을 주면, 모델이 스스로를 강화하는 쪽으로 흘러간다.
  • 설정 부채: 어떤 피처를 썼는지, 전처리를 어떻게 했는지, 어떤 기간의 데이터로 학습했는지 같은 설정이 코드보다 많아진다. 이게 관리되지 않으면 재현이 안 된다. 앞에서 말한 “어떤 모델과 전처리가 최적이었는지 추적하기 어렵다"가 딱 이 경우다.

DevOps와의 차이

그럼 DevOps랑은 뭐가 다를까. ML 시스템은 바뀌는 대상부터 다르다.

DevOpsMLOps
바뀌는 것코드코드, 데이터, 모델
테스트 대상코드, 컴포넌트여기에 데이터 검증, 모델 품질 검증이 더해짐
자동화CI/CDCI/CD + CT(Continuous Training, 지속 학습)
배포 후 성능 변화주로 코드나 인프라가 바뀔 때코드가 그대로여도 데이터가 바뀌면 떨어짐

Google Cloud의 MLOps 문서는 이 차이를 CI, CD, CT로 설명한다.

  • CI: 코드뿐 아니라 데이터와 모델까지 검증한다.
  • CD: 모델 파일 하나가 아니라 “모델을 학습시키는 파이프라인"을 배포한다.
  • CT: 새 데이터가 들어오면 모델을 자동으로 다시 학습시켜 내보낸다.

핵심

배포 후에도 데이터에 따라 성능이 변하니까 모니터링이 선택이 아니라 필수가 된다.

MLOps란

위 내용을 묶으면, MLOps는 모델을 만드는 일(Dev)과 그 모델을 서비스로 굴리는 일(Ops)을 하나로 이어서, 모델이 계속 제 성능으로 돌아가게 만드는 방법이다. Google Cloud 문서는 MLOps를 이렇게 정의한다.

ML 시스템의 개발(Dev)과 운영(Ops)을 통합하려는 ML 엔지니어링 문화이자 실천 방식

— Google Cloud MLOps 문서

구체적으로는 아래 구성 요소들로 이뤄진다.

  • 실험 추적: 어떤 코드, 데이터, 파라미터로 어떤 결과가 나왔는지 기록
  • 모델 레지스트리: 모델 버전과 “지금 운영 중인 모델” 관리
  • 저장소: 모델 파일, 산출물, 메타데이터 보관
  • 서빙: 등록된 모델을 추론 서버로 내보내기
  • 오케스트레이션: 학습 → 평가 → 등록 → 배포를 파이프라인으로 자동화
  • 모니터링: 서빙 지표와 데이터 드리프트 감시
  • 하이퍼파라미터 탐색: 탐색 결과를 실험 추적과 연결
  • 데이터 버전 관리, 피처 스토어: 언제 필요한가

정리

  • 실제 ML 시스템에서 모델 코드는 일부일 뿐이고, 대부분은 데이터, 설정, 서빙, 모니터링 같은 주변부다.
  • ML은 코드뿐 아니라 데이터와 모델도 바뀌어서, DevOps의 CI/CD에 데이터·모델 검증, CT, 모니터링이 더해진다. MLOps는 이걸 체계적으로 관리하는 방법이다.
