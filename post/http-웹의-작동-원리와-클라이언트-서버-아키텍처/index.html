HTTP-웹의 작동 원리와 클라이언트-서버 아키텍처

Apr 05, 2026
5 minute read

백엔드 분야에 대한 과목이 학부 때 존재했지만, 이미 전공과목의 학점을 다 들었다는 이유로 수강하지 않았었고, 네트워크 이론 등 여러 중요 CS 과목들도 기억에서 희미해져 가기 때문에,,, 독학을 통해 백엔드 분야의 이론과 실습을 학습해 보고 이를 기록해보려고 한다.

백엔드라는 분야는 웹페이지가 생기고 발전해 오면서 함께 방대해진 분야이다. 또, 백엔드는 프론트엔드와 반대되는 느낌의 분야라고 느껴진다. 웹 애플리케이션, 모바일 애플리케이션 등의 응용 프로그램에서 서버, 데이터 베이스를 관리하고 데이터를 주고받는 기술이라고 이해할 수 있다. 프론트엔드는 사용자와 상호작용하는 프로그램의 앞부분을 만들고, 백엔드는 상호작용을 통해 생성되는 데이터나 동작들을 서버에 전달하고 데이터베이스에 기록하는 등의 여러 눈에 보이지 않는 부분을 만든다고 생각하면 될 듯하다.

백엔드 분야를 잘 이해하기 위해서는 웹이 어떻게 동작하고, 동작을 담당하고 구성하는 요소들이 어떤 게 있는지 잘 알아야 할 필요가 있다. 그래서 웹에 대한 부분과 HTTP 기초 이론들을 시작으로 백엔드 학습을 시작하려 한다.

1. 웹의 작동 원리

  • 웹의 정의와 구성요소

    • 웹(web): 인터넷에 연결된 컴퓨터들 간에 정보를 공유하는 시스템. 주요 구성요소는 HTML, URL, HTTP이다.
    • HTML: 웹 페이지의 내용과 구조를 정의한다. 만약 네이버라는 웹페이지를 만든다면, 검색창이 어디에 위치해 있고, 로그인 버튼의 크기는 어디에 있고 등을 정의해 둔 문서를 네이버 회사의 서버에 저장해 두게 된다. 이를 chrome, edge 등의 응용프로그램으로 웹페이지를 보여주게 되는 것. (CSS를 통해 이 문서에 정의해 둔 요소들을 예쁘게 꾸며줄 수 있다.)
    • URL: Uniform Resource Locator의 준말로, 웹 상의 자원을 찾기 위한 주소이다.
    • HTTP: HyperText Transfer Protocol의 준말로, 클라이언트와 서버 간 웹 문서(HTML)를 주고받는 데 사용되는 프로토콜이다. 

  • 웹 페이지의 요청 및 응답 과정

웹 페이지를 요청하고 응답하는 전반적인 과정을 간단히 살펴보면 아래와 같다.

과정을 조금 더 자세히 알아보면 아래와 같은 과정을 거친다.

  1. 사용자의 웹페이지 요청
    • 사용자의 동작: 사용자는 웹 브라우저에 URL을 입력한다. 예를 들어, ‘https://www.google.com/'를 입력합니다.
    • URL 분석: 브라우저는 URL을 분석해 프로토콜(‘https’), 호스트 이름(‘www.google.com’), 자원의 경로(’/’)를 파악한다.
  2. 도메인 이름 시스템 조회
    • DNS 조회: 브라우저는 ‘www.google.com’의 IP주소를 알아내기 위해 DNS 조회를 한다. 이를 통해 DNS 서버는 도메인 이름을 그에 해당하는 IP 주소로 변경하게 된다! ‘www.google.com’ -> ‘172.217.25.164’
    • 사용자들이 기억하기 좋고 입력하기에도 쉬운 도메인 주소를 지정하고, 패킷이나 데이터의 라우팅에는 IP 주소가 필요하므로 DNS 서버에서 도메인 주소와 IP주소를 변환해 준다.
  3. 서버에 대한 요청
    • IP주소를 사용한 요청: DNS 조회를 통해 얻은 IP 주소를 사용해, 브라우저는 해당 서버에 HTTP 요청을 보낸다.
    • HTTP 요청: 이 요청에는 ‘GET’ 메서드(웹 페이지 요청), 요청 헤더(브라우저 정보, 콘텐츠 유형 등)가 포함된다.
  4. 서버의 처리 및 응답
    • 서버의 요청 처리: 서버는 HTTP 요청을 받고, 요청된 URL에 해당하는 웹 페이지나 자원을 처리한다.
    • HTTP 응답: 서버는 처리한 결과를 HTTP 응답으로 사용자의 브라우저에 보낸다. 이 응답에는 상태 코드 (200 OK, 404 not found 등!), 응답 헤더, 요청된 웹 페이지의 알맹이(HTML 등)가 포함되어 있다.
  5. 웹페이지 렌더링
    • 브라우저의 응답 처리: 브라우저는 서버로부터 받은 HTTP 응답을 읽어낸다.
    • 웹 페이지 렌더링: 브라우저는 HTML, CSS, JavaScript 등을 해석하여 웹 페이지를 화면에 렌더링 한다.
  6. 추가 자원 로드
    • 웹 페이지에 추가 자원(이미지, CSS, JavaScript 파일 등)이 포함된 경우, 브라우저는 추가 HTTP 요청을 통해 이러한 자원을 로드하고 페이지를 완성하여 사용자에게 보여준다!!

닫기

여러 가지 주소들!

웹 페이지를 요청하고 응답하는 과정에서 많은 주소들이 언급되고 사용된다. 이를 간략히 정리해 보자.

  1. URL (Uniform Resource Locator)
    • 정의: URL은 인터넷 상의 자원의 위치를 가리키는 주소이다. 웹 페이지, 이미지, 비디오 등의 위치를 나타내는 데 사용된다.
    • 구성요소: 프로토콜(예: http, https), 호스트 이름(예: www.example.com), 경로(예: /index.html, /home)
    • 용도: 웹 브라우저에서 특정 웹 페이지나 자원을 직접 요청하는데 사용된다.
  2. URI (Uniform Resource Identifier)
    • 정의: URI는 인터넷 상의 자원을 식별하는 통합된 방식이다. URL은 URI의 하위 개념!!
    • 용도: URL이 위치를 가리키는 데 반해, URI는 자원을 식별하는 데 넓게 사용됩니다. 예를 들어, ‘mailto:example@example.com’은 이메일 주소를 식별하는 URI이다.
  3. IP 주소 (Internet Protocol Address)
    • 정의: IP 주소는 인터넷 상의 장치(서버나 컴퓨터)를 식별하는 데 사용되는 고유한 숫자 주소이다.
    • 용도: 네트워크 상에서 장치간 데이터를 전송할 때 목적지와 출발지를 식별하는 데 사용된다.
    • IPv4와 IPv6가 사용되고있다.
  4. DNS 주소(Domain Name System)
    • 정의: DNS는 사람이 읽을 수 있는 도메인 이름을 IP 주소로 변환하는 시스템이다. DNS 주소라고도 하지만 보통은 도메인 이름이라고 부른다.
    • 용도: 사용자가 도메인 이름을 사용하여 웹 사이트에 접근할 수 있도록 도와준다. IP로 바꾸기!

비교

  • URL vs URI: URL은 웹 자원의 위치를 가리키는 구체적인 주소이고, URI는 웹 자원을 넓게 식별하는 주소(식별자).
  • URL/URI vs IP 주소: URL과 URI는 웹 자원의 식별 및 위치 지정에 사용되며, IP 주소는 인터넷 상의 장치를 식별하는 데 사용된다.
  • Domain Name vs IP 주소: Domain Name은 사용자가 편하게 기억하고 입력하게 가능한 주소이며 이를 IP 주소로 바꿔주는 시스템이 DNS 시스템이다. 실제 라우팅이나 데이터의 이동은 IP 주소를 사용한다.

시간이 지나면서 변경되고 추가되는 프로토콜이나 기술 등이 존재하지만, 기본적인 웹 페이지의 요청/응답 과정은 위 순서를 크게 벗어나지 않을 것으로 이해된다.

2. HTTP와 TCP/IP

HTTP와 TCP/IP에 대해서도 간략하게 알아보고 넘어가려 한다. HTTP는 위에서 언급했듯이, 웹에서 데이터를 교환하는 데 사용되는 프로토콜이다. 주로 HTML 문서와 같은 리소스를 요청하고 전달하는 데 사용된다. 그러면 TCP/IP는 무엇일까?

TCP/IP

  • 정의: TCP/IP (Transmission Control Protocol / Internet Protocol)는 인터넷에서 데이터를 전송하는 데 사용되는 기본 프로토콜 모음이다. 
  • 신뢰성 있는 데이터 전송: TCP는 데이터가 목적지에 안정적으로 도달하도록 보장한다. 데이터 손실이 발생할 경우 재전송을 수행한다.
  • IP 주소와 라우팅: IP 주소를 통해 데이터 패킷은 출발지부터 목적지까지 라우팅 된다.
  • HTTP와 TCP/IP의 역할: HTTP는 TCP/IP의 상위 계층에서 작동한다.(OSI 7 Layer에서 확인 가능) 웹 통신에서 HTTP는 데이터와 리소스의 교환을 담당하고, TCP/IP는 이러한 데이터가 네트워크를 통해 안정적으로 전송되도록 보장한다.

OSI 7 Layer의 내용을 함께 다루면 좋겠지만, 다른 포스팅을 통해 더 자세히 다루고 싶어 일단 여기까지 작성하고 다음 내용으로!

3. 클라이언트 - 서버 아키텍처

클라이언트-서버 모델은 서비스 요청자인 클라이언트와 서비스 자원의 제공자인 서버 간에 작업을 분리해 주는 분산 애플리케이션 구조이자 네트워크 아키텍처를 나타낸다. 각 요소의 역할은 이렇다.

  • 클라이언트: 사용자 인터페이스와 관련된 작업을 수행하고, 서버에 서비스를 요청한다. 일반적인 예로는 웹 브라우저가 있다.
  • 서버: 클라이언트의 요청에 대해 필요한 데이터나 서비스를 제공한다. 데이터베이서, 파일, 웹 페이지 등을 관리하고 클라이언트에게 전송한다.

위의 웹 페이지 요청 및 응답 과정에서 USER에 해당하는 부분이 클라이언트라고 할 수 있고, SERVER가 서버의 부분이라고 할 수 있다. 실생활에 사용되는 많은 애플리케이션이나 서비스들이 클라이언트-서버 구조를 띄고 있다!

하지만 이 구조에도 장/단점은 존재한다. 중앙 집중화로 인해 리소스 관리가 용이하고, 유지보수가 효율적이라는 장점이 있지만, 서버에 과부하가 걸릴 경우 성능 저하가 발생할 수 있으며, 서버가 다운되면 서비스 전체가 영향을 받는다는 치명적인 단점이 있다!

오늘은 백엔드 개발의 본격적인 공부에 앞서서 기초적인 몇 가지 이론들을 살펴보았다. 현대에 이르러서는 많은 구조적 변경과 다양한 기술들이 도입되어 더 배울 것들이 많아졌지만, 기초적인 부분부터 차근차근 배워나가야 할 것 같아 한번 정리를 해보게 되었다.
